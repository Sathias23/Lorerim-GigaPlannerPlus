## Direct answers

**Q1: Agent Skills today.** A skill is a folder with a SKILL.md: YAML frontmatter plus a Markdown body. Optional scripts/, references/ and assets/ folders sit beside it. The format is an open spec at agentskills.io, which ships a `skills-ref` validator. `name` (≤64 chars, lowercase and hyphens, must match the folder) and `description` (≤1024 chars, what the skill does plus when to use it) are required. Loading is progressive:
- **Startup:** only name and description are always in context (about 100 tokens per skill).
- **Activation:** the body is loaded (under 500 lines / under 5k tokens recommended).
- **On demand:** references are read and scripts are executed, and only script output costs tokens.

In Claude Code, skills live in `~/.claude/skills`, `.claude/skills` or plugins, or are synced from claude.ai. Each skill is also a `/slash-command`, and the model auto-invokes it by matching the description. The listing truncates description + when_to_use at 1,536 chars. Claude Code-only frontmatter includes `disable-model-invocation`, `paths`, `context: fork`, `allowed-tools` and others. In claude.ai, skills need code execution enabled, are uploaded as a ZIP, and trigger automatically from the description. The support article I read does not name the Claude Desktop app specifically.

Auto-triggering is the known weak spot. Practitioners report missed activations, and a Dec 2025 bug silently dropped skills past a 15k-char description budget. A skill that must always run is safer invoked explicitly (`/skill`) or forced through a hook.

**Q2: Division of labour.** Anthropic's stated rule: MCP servers hold connectivity, data access and the rules for using their own tools correctly. Skills hold process: domain strategy, workflow order, output format and orchestration across tools. For this project **[inference]**:
- **Skill:** LoreRim build strategy, the design workflow (elicit, draft, validate, repair, present) and output formatting.
- **MCP server:** the catalog data plus the deterministic legality and budget engine.

Do not state output format in both places. Refer to MCP tools by their fully qualified names in the skill.

Anthropic also says to prefer bundled scripts for deterministic operations, since only their output enters context. A skill that shells out to the existing TS engine (e.g. `node scripts/validate.js <code>`) is therefore a legitimate alternative to MCP in Claude Code. **[inference]** It breaks down in claude.ai/Desktop because:
- skills there run in Anthropic's code-execution sandbox, not on your machine;
- synced skills never run shell injections locally;
- claude.ai may need packages installed;
- the Claude API sandbox has no network.

The MCP server is the one surface that serves both Claude Code and Claude Desktop from the same local engine. A reasonable split is MCP for the engine, the skill for know-how, and optionally a thin script fallback in Claude Code.

**Q3: Tool design for agents.** Anthropic's engineering post (Sep 2025) says:
- **Consolidate** into workflow-shaped tools rather than CRUD (e.g. one `validate_build` / `apply_changes` rather than add_perk/remove_perk/get_budget).
- **Namespace** with a consistent prefix.
- **Return human-meaningful identifiers** rather than opaque UUIDs.
- **Offer a `response_format` concise/detailed enum.**
- **Paginate, filter and truncate** with sensible defaults, and write truncation notes that point to narrower queries.
- **Write errors that say how to fix the problem.** The skills doc gives the example "Field X not found. Available fields: ...", which suits illegal perks: name the unmet skill or level requirement and the remaining budget.
- **Treat descriptions as prompts,** with unambiguous parameter names.
- **Drive iteration with evals:** realistic multi-call tasks, transcripts analysed by Claude. The skills doc separately asks for at least three eval scenarios against a no-skill baseline.
- **Mind the client's output cap:** Claude Code limits MCP results to 25k tokens by default (warning at 10k), so responses must stay compact.

Tool Use Examples (`input_examples`) are an API feature. I did not confirm that MCP or Claude Code can surface them.

**Q4: Searching a large catalog cheaply.** Anthropic's patterns all avoid dumping the catalog into context. The approaches:
1. **Search/filter tool:** query plus filters (skill, tree, requirement level), paginated, with concise responses by default and full detail on request. This follows the engineering post, and **[inference]** it is the most portable option for Claude Code + Desktop.
2. **Code execution:** the agent writes code that filters the data in a sandbox and returns only aggregates. It cut 150k tokens to 2k in the example, but it needs a sandbox. Programmatic Tool Calling is the API-side version.
3. **Skill-bundled reference files that the agent greps** (best-practices "Quick search" pattern). No context cost until read, but it needs filesystem access: fine in Claude Code, and it only works in the claude.ai sandbox if the data is inside the skill ZIP.

Claude Code's MCP Tool Search only defers tool *definitions*. It does not help with catalog data.

I did not verify how MCP resources are surfaced or loaded in Claude Code or Claude Desktop in this run. **[unverified belief]** Resources are application-controlled (the client or user attaches them), so they are a poor fit for model-driven lookup across hundreds of perks.

With a few hundred perks, a search tool that returns compact rows is the lowest-risk design. **[inference]**

**Q5: Stateful vs stateless.** The strongest current evidence is the MCP 2026-07-28 spec, which removed protocol-level sessions. It explicitly recommends that a server needing state "mint an explicit handle from a tool and have the model pass it back as an argument", because the model can see the handle and thread it between tools. That rules out hidden, transport-bound "current draft" state. Two designs remain, and both fit the guidance:
- **Server-side draft keyed by a visible id,** e.g. a `draft_id` returned by `create_draft` and passed to later calls.
- **Fully stateless calls that pass a compact share code,** with each call returning the updated code. The code is the handle.

**[inference]**
- **Share code:** survives server restarts, is replayable, copy-pastable into the planner, and easy to eval deterministically. It costs input tokens on every call and is opaque to the model, so tools should also return a readable summary.
- **draft_id:** saves tokens but loses state when the stdio process restarts.

A hybrid is: stateless tools that accept either a share code or a build object, and always return the new share code plus a concise, human-readable diff and budget. I found no Anthropic-published A/B evidence that compares the two.

## Leads (contradictions first)

1. **Contradiction, MCP tool-name format.** The skills best-practices doc says to reference MCP tools as `ServerName:tool_name`, but Claude Code names them `mcp__server__tool`. Check which form actually resolves in Claude Code vs claude.ai/Desktop, or whether both do.
2. **Contradiction or staleness, description budget.** The Dec 2025 pain point describes a global `SLASH_COMMAND_TOOL_CHAR_BUDGET` of 15k chars. Current docs describe a per-skill 1,536-char truncation. Confirm whether the global budget still exists and what it defaults to now.
3. **Claude Desktop specifically:** does it support skills like claude.ai web? How does a local stdio MCP server get installed (claude_desktop_config.json vs .mcpb Desktop extensions)? Does Desktop honour the 2026-07-28 stateless spec and the 25k-style output caps?
4. **MCP client support for the 2026-07-28 spec** in Claude Code and Desktop. Is the TS SDK version backward compatible with older clients?
5. **MCP resources and prompts in Claude Code** (the @-mention and slash-command surfaces), plus `structuredContent` / outputSchema support. This decides whether catalog resources or prompts are worth building.
6. **Primary data on skill activation rates:** the 650-trial Medium study (blocked, 403). Also check whether hooks or `when_to_use` measurably improve triggering.
7. The anthropics/skills repo's `mcp-builder` skill is likely to hold Anthropic's concrete MCP tool-design checklist (tool naming, pagination defaults, response formats). I did not read it this round.
