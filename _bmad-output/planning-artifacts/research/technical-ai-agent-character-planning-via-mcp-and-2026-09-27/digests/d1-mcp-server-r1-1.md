## Direct answers

**Q1: The SDK and the spec.** The official TypeScript SDK is at v2. For a server, install `@modelcontextprotocol/server`; the latest release seen is 2.1.0, around 2026-09-23. It uses Standard Schema, so Zod v4, Valibot or ArkType all work. The API is `McpServer` + `registerTool(name, {description, inputSchema: z.object(...), outputSchema?}, handler)` + `StdioServerTransport` from `/server/stdio`. The v1 line, `@modelcontextprotocol/sdk` 1.30.x, still gets fixes for at least 6 months after v2. The current spec is 2026-07-28, which is stateless: no initialize handshake, per-request version `_meta`, and `server/discover`. Tools may declare `outputSchema`, and then MUST return a conforming `structuredContent`. They SHOULD also return the same JSON as a text block. For this project, that means a tool like `compute_build` can return typed structured results (the budget, remaining perk and skill points, violations) plus a text copy. Anything the planner needs to carry between calls, such as a build in progress, should be an explicit handle argument or the share code itself, not session state. The version number rests on one source, because npm was not checked.

**Q2: Transport and installation.** Claude Code has two routes. One is `claude mcp add --scope project|user|local <name> -- node <abs>/server.js`. The other is a committed `.mcp.json` (`{mcpServers:{name:{command,args,env}}}`). For Claude Desktop, the one-click route is an MCPB `.mcpb` bundle (`mcpb init` / `mcpb pack`, bundling `node_modules`; Desktop ships its own Node on macOS and Windows). The claude_desktop_config.json route was not re-read in this run. A Claude Code plugin can package the MCP server together with the companion skill: `.claude-plugin/plugin.json`, `skills/<name>/SKILL.md`, and `.mcp.json` or inline `mcpServers`, which can even point at a `.mcpb`. Paths use `${CLAUDE_PLUGIN_ROOT}`, and node_modules go in `${CLAUDE_PLUGIN_DATA}`. That makes one plugin a single artifact for Claude Code, with a `.mcpb` of the same server for Desktop.

**Q3: Practical limits.** Tool output warns at 10k tokens and is capped at 25k tokens by default. Raise the cap with `MAX_MCP_OUTPUT_TOKENS`, or per tool with `_meta["anthropic/maxResultSizeChars"]` (at most 500k chars). Output over the limit is spilled to a file rather than truncated. Tool search (deferred loading) is on by default, so a large tool count costs less context than before. However, no primary numeric guideline for 'too many tools' was retrieved in this run. On Windows, `npx` needs `cmd /c`, and the `claude mcp add` CLI mangles `/c` into `C:/` (a closed, not-planned issue). A likely way to avoid all of this, not yet verified: run a bundled `node C:/…/dist/server.js` directly instead of npx, because node.exe is a real executable.

**Q4: Tools vs resources vs prompts.** In Claude Code, prompts (slash commands) and resources (`@server:uri`, plus model-driven List/ReadMcpResource tools) are supported (from a secondary source that cites the docs). Claude.ai connectors are reliable only for tools, and the Desktop app was not separately verified. So a large static JSON dataset should not be pushed wholesale through resources or into a single tool result. The 25k-token cap and the unreliable resource support outside Claude Code both argue for narrow query tools, such as search_perks, get_perk, list_races and get_skill_tree, that return filtered structured slices. Resources can be offered as an optional extra for Claude Code users.

**Q5: Reusing browser/Vite TypeScript in Node.** Node's native type stripping (default from 22.18, stable from 24.12) works only if the engine code is erasable-only (no enums or parameter properties), uses `.ts` import extensions and `import type`, and uses no tsconfig `paths` aliases. Typical Vite source breaks at least some of these. Bundling to one file with esbuild/tsup is the usual escape hatch: it resolves aliases, inlines JSON, and handles extensionless imports. It is also what MCPB and plugins want, because it ships one `server.js` with minimal `node_modules`. tsx is fine for development. `import.meta.env` / `import.meta.glob` and JSON imports without `with {type:'json'}` are Vite-specific hazards. This run found no source for those pitfalls, so they are unverified beliefs.
